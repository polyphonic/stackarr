# Draft instance metadata transports

The catalog is a list of canonical app definitions, **not** installed/configured apps. Instances here are draft metadata records only. Creating, renaming, or removing a draft does not install an app, change a container, or affect an existing runtime.

The same version-1 DTO and core action are used by HTTP (`GET /api/v1/app-definitions`, `GET/POST /api/v1/instances`, `PATCH/DELETE /api/v1/instances/{id}`, `GET/POST/DELETE /api/v1/instances/{id}/connections`), MCP, and CLI. The operations and risk/scope mapping are declared in `packages/core/src/instanceOperations.ts`.

CLI: `stackarr instances catalog`, `stackarr instances list [--limit 1..100] [--cursor UUID]`, `stackarr instances create` (JSON `{ "definitionId": "sonarr", "displayName": "TV", "ownership": "managed" }` on stdin), `stackarr instances rename UUID` (JSON `{ "displayName": "TV 2" }` on stdin), `stackarr instances remove UUID --yes`. JSON input is limited to 16 KiB; private configuration and secret-reference fields are not accepted. Host CLI runs the installed controller; it does not create a host-side fallback database.

MCP tools: `stackarr_list_app_definitions`, `stackarr_list_instance_drafts`, and `stackarr_list_instance_connections` are readable in observe; `stackarr_create_instance_draft`, `stackarr_rename_instance_draft`, and `stackarr_connect_instance_drafts` require manage/write; `stackarr_remove_instance_draft` and `stackarr_disconnect_instance_drafts` are dangerous and require admin plus the existing interactive approval flow (unless deliberately using unrestricted authority). No generic shell or Docker operation is exposed. Store failures return `store_unavailable` without database or connection details; invalid inputs and absent IDs return `invalid_input` and `not_found`.

HTTP currently uses the install-wide ADMIN API key or signed dashboard session via `requireApiKey`, not a scoped MCP credential. This is an explicit transport exception to the MCP risk/scope approval policy; a scoped MCP token is not HTTP admin authority. Dangerous HTTP `DELETE /api/v1/instances/{id}` and `DELETE /api/v1/instances/{id}/connections` require `x-stackarr-confirm: true` (header name case-insensitive, value exactly `true`) before mutation, in addition to authentication. Connect POST remains ordinary authenticated, same-origin write without that confirmation. Existing instance DELETE still forbids a body; connection DELETE still requires exactly `{ "targetId": "UUID", "kind": "download-client" }`. CLI `--yes` and MCP dangerous approval are unchanged.

Mutation responses include `audit: { id, status }`. `recorded` means the activity result was read back. `degraded` means the mutation succeeded but its final audit record could not be verified. Do not retry a successful mutation because its audit status is degraded. Failure to persist and verify the initial audit record prevents mutation. Audit summaries contain only the operation, validated instance UUID, and outcome.

All draft MCP inputs reject unknown fields. Rename bodies accept only `displayName`, never an `id`, including one matching the path or CLI argument. Existing instance HTTP DELETE rejects any request body; connection DELETE requires the exact `{targetId,kind}` body. Only CLI `create` and `rename` read JSON from stdin. CLI mutations use explicit UUIDs and `--yes` arguments and do not interpret stdin as configuration. CLI instance failures exit nonzero and write a JSON `error` object with `code` and `message` to stderr, without a Node stack trace.

This is source-only draft functionality. Disposable PostgreSQL upgrade/restore, real controller dispatch, app configuration, lifecycle, legacy runtime migration, and the completed Add App flow still require qualification. The SQLite upgrade tests and captured PostgreSQL SQL do not establish live PostgreSQL acceptance.

## Draft connection graph

Migration `20261108` adds `app_instance_connections` with immutable instance IDs, restrictive foreign keys, and unique `(source_id, target_id, kind)`. The public core actions are `connectDraftInstancesAction({sourceId,targetId,kind:'download-client'})`, `disconnectDraftInstancesAction` with the same input, and `listDraftInstanceConnectionsAction({instanceId,limit?,cursor?})`. Each connection DTO has `schemaVersion: 1`, `sourceId`, `targetId`, and `kind`. The list returns `{schemaVersion:1,items,nextCursor}` for incoming and outgoing edges, ordered by source and target ID, with limit 1–100 (default 100) and a `sourceUUID:targetUUID` cursor. SQL fetches at most limit+1. Duplicate connects are idempotent. Missing instances return `not_found`; invalid fields, self edges, unsupported kinds and pairings return `invalid_input`. Removing an instance with any edge returns typed `conflict` (HTTP 409 for the existing remove route); disconnect only removes the named edge.

Only Sonarr, Radarr, or Lidarr → qBittorrent or Transmission is supported as optional `download-client` metadata. Several sources can share a downloader or connect independently. No downloader is selected implicitly or enabled, and an external/native instance remains external/native; these actions neither install nor configure anything. Required dependencies and all other connection kinds remain unsupported until their upstream capabilities and lifecycle consequences are audited. HTTP POST/DELETE take path source UUID and only `{targetId,kind:'download-client'}` in a bounded body. CLI uses `stackarr instances connections ID [--limit N] [--cursor SOURCE:TARGET]`, `stackarr instances connect SOURCE TARGET --yes`, and `stackarr instances disconnect SOURCE TARGET --yes`. Connection audit evidence carries only action, validated source/target UUIDs and outcome. PostgreSQL behavior has SQL source/capture evidence only, not a live upgrade or concurrency qualification.
