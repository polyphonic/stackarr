# Updates

Use `alpha` for the moving early-access channel or a versioned tag for a repeatable deployment:

```dotenv
STACKARR_IMAGE=polyphonic/stackarr:alpha
```

## Update from Stackarr

Stackarr separates controller updates from the apps it manages. This keeps an
unavailable or locally built Stackarr image from blocking updates for Plex,
the Arr apps, download clients, and the rest of the enabled stack.

Ask an admin-profile agent to back up and update the managed apps, use
**System → Updates → Update apps**, or run:

```bash
docker exec app /app/bin/stackarr update services
```

The app workflow targets managed services explicitly, leaves the Stackarr
controller and its database running, and reapplies integrations. Cleanup runs
only after integration reconciliation, which can recreate a downloader again.
Before cleanup, selected containers with Docker health checks must remain
healthy for 10 seconds. Containers without health checks must remain running
without a restart for 30 seconds. That observation is not
proof of application health. Missing, exited, restarting, unhealthy, replaced,
or timed-out containers fail the update and skip cleanup, preserving old images
for recovery. The default readiness wait is five minutes. The scheduled update
job uses this same workflow. A pulled image alone is not a successful update.

Cleanup enumerates exact image IDs and rechecks container references and tag
sets before non-forced deletion. Images referenced by running **or stopped**
containers are preserved, including their tags; persistent volumes are not
pruned. Other unused images, including tagged rollback images with no container
reference, can be deleted by this user-initiated or scheduled workflow. There
is no age grace period. Keep a stopped container referencing an image you need
to retain, or disable managed updates until you have a separate retention plan;
do not treat a repository digest or tag alone as protection. If readiness fails,
cleanup is skipped. If cleanup itself fails, the update task reports failure
even if some services were already replaced.

Persistent Docker volumes are not pruned automatically. First use
`stackarr_get_container_overview` to review every unused volume. After confirming
that a specific volume's data is no longer needed, call
`stackarr_remove_docker_volume` with its exact name as `id`,
`confirmDangerous: true`, and a reason. Repeat for each reviewed volume. Stackarr
rejects bulk volume pruning so the confirmation cannot sweep up unrelated
volumes that became unused later.

When an older RomM or FlareSolverr container still uses an image-declared
anonymous volume, the next managed Compose reconciliation copies its data into
the new stable named volume and verifies the copy before recreation. The
original volume is retained for manual review; remove it only after the
recreated service is healthy and its data is present.

Stackarr defaults application services such as Youtarr and tinyMediaManager to
their upstream stable moving tags so this workflow keeps them current. Stateful
infrastructure such as database engines stays version-pinned when an automatic
major upgrade could break persisted data or configuration. Every image remains
runtime-configurable when an installation needs a deliberate version pin.

## Update only the Stackarr app

Use **System → Updates → Update Stackarr**, or run:

```console
docker exec app /app/bin/stackarr update app
```

The running controller hands this operation to a one-shot maintenance worker.
That worker pulls only the Stackarr image, reconciles database access, recreates
only the controller, waits for its health endpoint, and records the result in
Activity. Other services stay online.

When `STACKARR_IMAGE` ends in `:local`, Stackarr keeps that image and explains
that it must be rebuilt from its source checkout. Managed app updates still run
normally.

The legacy `stackarr update run` command remains an alias for
`stackarr update services`.
