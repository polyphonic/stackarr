# Custom PostgreSQL server

Stackarr's default is the unified, managed TimescaleDB/PostgreSQL container. **App defaults** keeps Stackarr state in SQLite while PostgreSQL-dependent apps still use that container. **Shared Postgres** also moves supported Stackarr/Arr state into separate databases there. Do not change the image or server just to inspect extensions.

## Before selecting an external endpoint

In **Settings → General → Advanced**, select bundled managed TimescaleDB or an existing native/external PostgreSQL server. External mode needs a server host and port reachable **from the Stackarr and app containers**. `localhost` inside a container is that container, not the Docker host. Use a Docker-reachable host address or DNS name; do not expose the database to the public internet. Configure separate databases and app roles with `CONNECT`, ownership and schema privileges their applications require. Arrange TLS/network access and role passwords with the external server administrator. The mode and host/port controls are connection configuration, not a provisioning or data migration wizard. Saving through `PUT /api/v1/config/stackarr` stores and projects the selected endpoint into participating client settings; it does **not** test the proposed endpoint, transfer data, create roles/extensions or apply/restart clients. Existing per-app URLs/credentials need explicit review: a URL pointing to a different endpoint can cause projection to reject the save, and saved explicit URL credentials can take precedence in diagnostics. Do not assume the server superuser field applies to an external instance. Apply/reconcile only after reviewing every client and a current verified backup. A host-local address or native backup connection is distinct from a container endpoint.

Stackarr's diagnostics panel uses the configured app roles, not an elevated server account. Refresh reports reachability and engine version, a bounded inventory of **installed and available extensions in each configured app database**, and selected server settings (`shared_preload_libraries`, `max_connections`, `work_mem`, `maintenance_work_mem`, `max_wal_size`) including `pending_restart`. Hidden or unavailable setting values are marked restricted rather than healthy. An extension being available on the server does **not** mean it is installed in an app database; installed entries remain visible even if absent from the available catalog. The "provisioning contract" label is derived only from Stackarr's inspected app provisioning: BookOrbit (`uuid-ossp`, `pg_trgm`, `vector`), Immich (its selected vector variant with `cube` and `earthdistance`), and Tracearr (`timescaledb`) when enabled. These are conditional, not universal server requirements. Other apps may install their own extensions; inspect their upstream requirements separately. Permissions or unreachable endpoints appear as explicit states rather than empty inventories. Up to 32 configured app/database associations and 128 extension rows per database are shown; truncation is marked. Inspection runs with at most four concurrent clients and an eight-second request deadline; remaining targets are marked unreachable. This is not an estate-wide discovery of unrelated databases.

The authenticated `GET /api/v1/database/diagnostics` route provides the same read-only saved-state inspection. Existing MCP operations include `stackarr_list_service_configs` and `stackarr_get_service_config` for service settings and `stackarr_get_postgres_backup_status`, `stackarr_test_postgres_backup`, and `stackarr_run_postgres_backup` for the **separate remote archive target**. These are not a draft external-endpoint test, migration, extension installer or server restart. Do not use a remote archive target test as proof that the selected application database endpoint is ready.

Diagnostics follows the existing application connection behavior: an app URL's explicit `sslmode` is honored; an absent URL mode and field-based credentials currently use `disable` (including external deployments). External host/port settings do not yet expose a shared TLS policy. Do **not** treat a successful diagnostic as proof of encrypted transport. For a secure external deployment, configure TLS explicitly in each application's supported connection configuration and verify its actual connection; if your external server requires TLS and an app has only field-based credentials, defer cutover until an authenticated TLS configuration path is available. Diagnostics never silently retries with a weaker TLS mode.

For an extension, install the appropriate **server binaries** first, then enable it in each database that needs it with the privileges required by that extension. Some extensions require a matching entry in `shared_preload_libraries` and a server restart before creation or use; consult that extension's documentation and verify server/extension major-version compatibility. `pending_restart` is a read-only indication; editing a config file or changing a setting is not performed by Refresh. The diagnostics UI does not create extensions, alter settings, restart the server, or request superuser privileges. Managed changes need a separate reviewed, approval-gated workflow; external changes belong to the server owner. Do not mistake a missing available extension for a missing installed extension, or a running server for a ready app database.

## Safe sequence and rollback

The ownership selector is not a one-click rollback. After saving an external selection, client hosts, ports and URLs retain that selection. To return to managed mode, restore the recorded complete client configuration and credentials, including container-internal ports (PostgreSQL `5432`, Redis `6379`, MariaDB `3306`). Clear the external selectors in the same configuration update. Stackarr rejects retained external hosts or non-managed ports rather than silently redirecting clients to a potentially empty bundled database.

1. Record the original mode, endpoint, app roles/URLs and current data locations. Verify a restorable backup of the original server and non-PostgreSQL app files. Check a matching PostgreSQL major version and required extension binaries on the destination; enable extensions in **each** target database that needs them. Confirm required preload settings and any restart with the server owner.
2. Provision distinct databases/roles and restore/migrate existing data using your own matching-engine tools in a separate maintenance window. A blank database is not a migration. For Stackarr state, changing **App defaults** (SQLite) to **Shared PostgreSQL** is a separate data transfer decision; enabling external mode alone does not move it.
3. In Advanced, enter the container-reachable host/port and review per-app fields and URL credentials. Read-only **Refresh diagnostics** inspects the **saved** configuration, not unsaved edits. There is no draft endpoint test. A reachable server alone does not prove every app can connect, TLS is enforced, or data is complete. Save after reviewing the summary and warnings; separately reconcile only when the destination and a rollback are ready.
4. Verify every enabled app's data and transport, restore an archive into an isolated matching engine, and retain the original source until the cutover is independently validated. If validation fails, restore the recorded endpoint/mode and credentials, reconcile affected clients explicitly, and validate against the preserved original. Do not delete or overwrite the original database during rollback.

## Backup and migration boundaries

If scheduled PostgreSQL backup is already enabled, disable that schedule before changing deployment mode or backup-source capabilities. This is an explicit save gate, not an automatic transfer of the backup source. Arrange replacement protection before the maintenance window, then re-enable a verified source-appropriate schedule after validation. Selecting an external endpoint does not authorize stopping, recreating or removing its server; direct service-apply requests for external infrastructure are refused.

The diagnostics SQL runs in read-only transactions. The surrounding authenticated application route uses Stackarr's normal runtime-settings reader, which may initialize or normalize Stackarr-owned configuration. It is not a no-write inspector for the local settings store.

The managed-container PostgreSQL backup targets its configured managed source. Selecting an external application endpoint does **not** qualify it for that backup: arrange and verify source-specific capture and a disposable matching-engine restore with the external owner. File backups still cover non-PostgreSQL app state, but do not replace database dumps or restore trials. No existing databases or images are cleaned as part of diagnostics.
