# Database capture bundles

The standalone `stackarr/scripts/database-bundle.py` utility captures an **explicit plan**, not an automatically discovered estate. It is separate from scheduled local backups and remote PostgreSQL archives. It does not upload, encrypt, decrypt, restore live data or choose the destination for you. Output must be on a caller-verified external filesystem. Do not treat a bundle as a complete installation backup unless your plan explicitly covers every required source and you have tested recovery.

A plan supplies an `inventoryNote`, explicit `exclusions`, and up to 256 `sources` with unique IDs, engine (`sqlite`, `mysql`, `mariadb`, `redis`, `postgres`), owner and locator. Engine-specific checker, password environment variable, user, generation and trusted source container fields are required in the plan schema even when null. Credentials are read from the named environment variable, never written into the manifest. PostgreSQL sources are **existing format-1 archive generation directories**, not arbitrary live PostgreSQL URLs. For Plex SQLite use a compatible native SQLite checker. SQL/Redis sources use host:port; a trusted running source engine container can supply native tools. This is useful for media-independent staging when the scope is intentionally chosen, not a substitute for inventory and backup ownership review.

Capture and verification check manifest members, sizes and digests; a successful check does not prove application restore. MariaDB captures user databases and portable user/grant definitions; MySQL uses native tables. Triggers, routines and events are included, but concurrent DDL or grant changes are not transactionally covered across databases. A PostgreSQL generation may contain globals, roles and per-database dumps; a matching engine with extension binaries and server configuration is still needed for a restore trial. Coordinate writes, retain the original source, encrypt plaintext artifacts with the established backup-encryption pipeline before external transport, and independently restore into an isolated matching engine.

The [scheduled remote PostgreSQL archive](/docs/settings/postgres-backup) is a different feature: it sends full logical PostgreSQL generations to a dedicated PostgreSQL destination under verified TLS, but is not a file, Redis, MySQL or MariaDB backup. Its retention count defaults to four and accepts 2–30 generations; each successful run verifies bytes before pruning older generations in the same transaction. Changing retention does not require a repository format migration; `stackarr_backup_v1` names the format, not the generation number. Budget for retained full generations plus an in-flight copy and provider history/WAL costs. Generic external PostgreSQL deployment alone does not make that source remote-archive-ready: its backup adapter requires separate explicit source identity, client and TLS settings and fails closed without them. Host-only `independent` mode has separate requirements documented in the archive guide.
